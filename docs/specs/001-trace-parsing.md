# 001. Парсинг трейса

**Статус:** не начато
**Крейты:** `crates/core` (основная работа), `crates/cli` (команда `stats`)
**Оценка:** 3–5 вечеров, если Rust впервые

## Цель

Научить `jankscope-core` читать трейс Chrome в типизированные структуры Rust,
а CLI — печатать по нему короткую сводку:

```
$ jankscope stats fixtures/layout-thrashing.trace.json
events:   10561
duration: 2949.5 ms
phases:   X 4320 · I 3901 · b 945 · e 945 · s 126 · f 126 · P 125 · n 41 · M 28 · B 4
threads:  CrRendererMain (46120:1) · CrBrowserMain (46003:46003) · ...
top names:
  StyleRecalcInvalidationTracking  840
  StyleResolver::ResolveStyle      839
  ...
```

Анализа здесь ещё нет. Это фундамент: всё дальнейшее работает поверх этих структур.

## Чему научишься

**Rust**
- Cargo: зависимости, workspace, связь между крейтами (`cli` зависит от `core`).
- Модули: `mod`, `pub`, файлы `trace.rs`, `lib.rs`.
- `struct` и `enum`, в том числе `enum` с данными внутри вариантов (в TS такого нет, ближе всего discriminated union).
- `serde` и `#[derive(Deserialize)]`: как JSON превращается в структуры, `#[serde(rename)]`, `#[serde(default)]`, `#[serde(untagged)]`.
- `Option<T>` вместо `undefined` и `Result<T, E>` вместо исключений, оператор `?`.
- Свой тип ошибки и `thiserror`.
- Итераторы: `iter`, `filter`, `map`, `max_by_key`, `HashMap` и его `entry`.
- Первое столкновение с ownership: почему `&str` и `String` — разные вещи, кто владеет данными трейса.
- Unit-тесты прямо в файле и интеграционные тесты в `tests/`.

**Браузер**
- [Trace Event Format](https://docs.google.com/document/d/1CvAClvFfyA5R-PhYUmn5OOQtYMH4h6I0nSsKchNAySU): формат, в котором Chrome пишет трейсы.
- Какие процессы и потоки у Chrome (`CrBrowserMain`, `CrRendererMain`, `CrGpuMain`, compositor) и почему рендер страницы живёт в `CrRendererMain`.

## Немного теории: что такое трейс

Трейс — это JSON со списком событий. Каждое событие — что-то, что произошло в каком-то потоке в какой-то момент. Пример из нашей фикстуры:

```json
{"args":{},"cat":"disabled-by-default-devtools.timeline","dur":10,"name":"RunTask",
 "ph":"X","pid":46050,"tdur":10,"tid":46067,"ts":1740485496,"tts":789}
```

| Поле | Что значит |
|---|---|
| `name` | имя события: `Layout`, `Paint`, `FunctionCall`… |
| `cat` | категории через запятую: `"cc,benchmark,disabled-by-default-devtools.timeline.frame"` |
| `ph` | **фаза**, тип события (ниже) |
| `ts` | время начала в **микросекундах** от произвольной точки отсчёта |
| `dur` | длительность в микросекундах (только у фазы `X`) |
| `tts`, `tdur` | то же, но по CPU-времени потока; есть не всегда |
| `pid`, `tid` | процесс и поток |
| `args` | произвольный JSON, у каждого события свой |
| `id`, `id2`, `s`, `bp` | служебные поля для связанных и мгновенных событий |

Фазы, которые реально есть в нашем трейсе:

| `ph` | Значение | Сколько в фикстуре |
|---|---|---|
| `X` | Complete: событие с началом и длительностью | 4320 |
| `I` | Instant: мгновенное событие без длительности | 3901 |
| `B` / `E` | Begin / End: начало и конец, парные | 4 / 0 |
| `b` / `e` / `n` | асинхронные начало, конец и точка внутри | 945 / 945 / 41 |
| `s` / `f` | flow: стрелка «это событие вызвало то» | 126 / 126 |
| `P` | сэмпл CPU-профайлера | 125 |
| `M` | метаданные: имена процессов и потоков | 28 |

Обрати внимание: `B` есть, а `E` нет. Запись оборвалась посреди задачи. Реальные трейсы всегда немного грязные, и парсер не должен из-за этого падать.

### Подвохи, найденные в реальном трейсе

1. **Верхний уровень бывает двух видов.** Наш рекордер пишет `{"traceEvents": [...]}`. Формат также допускает голый массив `[...]`, а экспорт из DevTools добавляет рядом `"metadata": {...}`. Нужно поддержать все три варианта.
2. **`id` бывает и числом, и строкой.** В фикстуре встречаются `"id": 0` и `"id": "0x1"`.
3. **`id2` — объект**, например `{"local": "0x19"}`.
4. **`ts` в нашей фикстуре всегда целый, но формат разрешает дробный.** Храни как `f64` или явно реши иначе и запиши почему.
5. **`args` у каждого события свой.** Типизировать все `args` сейчас не нужно (и невозможно), храни как `serde_json::Value`. Типизацию нужных `args` сделаем в следующих спеках.
6. **Неизвестные фазы.** Если Chrome добавит новую, парсер не должен падать: нужен вариант вроде `Phase::Other(String)`.

## Что сделать

Шаги идут по возрастанию сложности. После каждого шага код должен компилироваться, а тесты проходить.

### Шаг 1. Зависимости и модуль

- Добавить в `crates/core` зависимости `serde` (с фичей `derive`), `serde_json`, `thiserror`.
- Создать модуль `trace` (`crates/core/src/trace.rs`) и объявить его в `lib.rs`.
- В `crates/cli` добавить зависимость на `jankscope-core` по пути.

> **Разберёмся:** что такое feature у крейта, чем `cargo add` отличается от ручной правки `Cargo.toml`, что значит `path = "../core"`.

### Шаг 2. Одно событие

Описать `TraceEvent` и научиться парсить **одно** событие из строки. Набросок формы, а не готовый код:

```rust
pub struct TraceEvent {
    pub name: String,
    pub cat: String,
    pub ph: Phase,
    pub ts: f64,
    pub dur: Option<f64>,
    pub pid: u32,   // подумай: хватит ли u32? что, если придёт отрицательное?
    pub tid: u32,
    pub args: serde_json::Value,
    // id, id2, s — по необходимости
}
```

Тест: парсинг события `RunTask` из примера выше даёт `ph == Phase::Complete` и `dur == Some(10.0)`.

> **Разберёмся:** `#[derive]`, почему поле `dur` — `Option`, и что делает `serde`, когда поля в JSON нет.

### Шаг 3. Фазы как enum

Сделать `Phase` перечислением с понятными именами (`Complete`, `Instant`, `Begin`, `End`, `AsyncBegin`, …) и запасным вариантом `Other(String)`. Однобуквенные коды из JSON должны превращаться в варианты.

Подсказка: у `serde` есть два пути — `#[serde(rename = "X")]` на вариантах или ручной `impl` через `String`. Попробуй первый, упрись в проблему с `Other(String)` и разберись, почему так.

> **Разберёмся:** enum в Rust против union-типов в TS, `match` и проверка, что разобраны все варианты.

### Шаг 4. `id` двух видов

Описать тип для `id`, который принимает и число, и строку. Это `#[serde(untagged)]` enum.

> **Разберёмся:** как `untagged` перебирает варианты и почему на больших трейсах это может быть медленно (вернёмся к этому, когда будем ускоряться).

### Шаг 5. Весь трейс и ошибки

```rust
pub struct Trace { pub events: Vec<TraceEvent> }

pub fn parse(json: &str) -> Result<Trace, ParseError>;
```

- Поддержать три формы верхнего уровня из подвоха 1.
- `ParseError` — свой enum на `thiserror`, с нормальным текстом ошибки.
- Сломанный JSON — это ошибка, а не паника. `unwrap()` в `core` запрещён.

> **Разберёмся:** `Result`, `?`, чем `panic!` отличается от ошибки и почему библиотека не должна паниковать.

### Шаг 6. Потоки и сводка

Добавить методы на `Trace`:
- `duration_ms()` — от самого раннего `ts` до самого позднего конца события. Учти, что у метаданных `ts: 0`.
- `thread_names()` — имена потоков из событий `M` с `name == "thread_name"`.
- `count_by_phase()` и `top_names(n)`.

> **Разберёмся:** итераторы, замыкания, `HashMap::entry`, почему метод принимает `&self`, а не `self`.

### Шаг 7. Команда `stats` в CLI

`jankscope stats <path>` читает файл, вызывает `core`, печатает сводку как в разделе «Цель». Аргументы пока разбирать через `std::env::args()`, `clap` будет позже.

> **Разберёмся:** `main` возвращает `Result`, коды выхода, чтение файла в `String`.

### Шаг 8. Маленькая фикстура для тестов

Большой трейс в git не кладём. Нужен `fixtures/tiny.trace.json` на 30–50 событий: по паре каждой фазы, одно событие с `id`-строкой, одно с `id2`, оборванный `B`. Вырезать его из большого трейса можно скриптом на Node или через `jq`.

- В `.gitignore` добавить исключение `!fixtures/tiny.trace.json`.
- Интеграционный тест в `crates/core/tests/`, который парсит tiny-фикстуру и проверяет количества.

## Готово, когда

- [ ] `cargo test` зелёный, есть unit-тесты на каждый подвох из списка выше.
- [ ] `cargo clippy` без предупреждений.
- [ ] `jankscope stats fixtures/layout-thrashing.trace.json` печатает сводку; числа совпадают с подсчётом на Node.
- [ ] Сломанный файл даёт понятную ошибку и ненулевой код выхода, без паники.
- [ ] В `core` нет `unwrap()` и `expect()` вне тестов.
- [ ] В `DECISIONS.md` записано хотя бы одно решение из этой спеки (например, `f64` для `ts` или `Value` для `args`).

## Что сознательно не делаем

- **Потоковый парсинг.** Сейчас читаем весь файл в память. На трейсах в сотни МБ это упрётся в память, и это отдельная спека.
- **Типизацию `args`.** Только `serde_json::Value`. Нужные `args` типизируем в спеках про анализ.
- **Выбор «правильного» потока рендерера.** В трейсе может быть несколько `CrRendererMain` (например, `about:blank` и наша страница). Это задача следующей спеки, про модель кадров.
- **`clap` и красивый вывод.**
- **Производительность.** Сначала правильно, потом быстро.
